# Implementation Plan: StetMobile Persistent Audio Capture

**Branch**: `010-mobile-persistent-audio-capture` | **Date**: 2026-07-19 | **Spec**: [spec.md](./spec.md)

## Summary

Move mobile live microphone ownership out of SenseVoice and FunASR into one persistent capture service. The production composition uses a built-in-microphone preference that does not advertise Bluetooth input support. AirPods high-quality recording remains available only through an explicitly constructed strategy.

## Technical Context

**Language/Version**: Swift, Swift Concurrency
**Primary Dependencies**: AVFoundation, Foundation, OSLog
**Target Platform**: StetMobile on iOS 17+, with iOS 26 high-quality AirPods support behind availability checks
**Testing**: Swift Testing plus physical-device route validation
**Constraints**: Keep RemoteIO warm for background keyboard dictation; do not change macOS capture behavior; tolerate `setPreferredInput` rejection

## Design

### Shared frame and capture boundary

`ASRAudioFrame` is the only live audio representation consumed by recognizers. `PersistentASRAudioCapture` owns a continuously running hardware backend and a separately synchronized frame gate. Preparing starts hardware; starting and stopping dictation only changes the single active handler.

### Input strategies

`builtInPreferred` configures `.playAndRecord`, `.default`, `.mixWithOthers`, and `.allowBluetoothA2DP`, activates the session, requests an available `.builtInMic`, and then verifies the actual route. A2DP keeps AirPods eligible as a high-quality playback output; the strategy never includes `.allowBluetoothHFP` or `.bluetoothHighQualityRecording`, so AirPods remain ineligible as an input.

`airPodsHighQuality` retains `.allowBluetoothHFP` and adds `.bluetoothHighQualityRecording` on iOS 26 or later. The production mobile composition does not select it.

### Resolution and fallback

The preference and the active route are modeled independently. A matching route produces `preferredInputActive`; any mismatch produces `systemFallback` with the actual input port types. Preference failure is logged but is not a capture failure.

### Recovery and lifecycle

The capture service observes real route availability changes, coalesces notifications arriving during recovery, reconfigures the session, and rebuilds the engine, tap, and converter without closing the frame gate. Notifications generated by category, override, or route-configuration application are ignored to prevent a policy loop. Full teardown cancels recovery, removes hardware resources, and deactivates the session with `.notifyOthersOnDeactivation`.

### Engine integration

The composition constructs one `PersistentASRAudioCapture(strategy: .builtInPreferred)` and injects it into the selected engine. SenseVoice owns only model loading, VAD, and decoding. FunASR owns only PCM16 encoding, queueing, WebSocket transport, and transcript assembly. The selectable coordinator already shuts down the old engine before constructing and starting the new coordinator.

## Complexity Tracking

| Area | Reason |
|---|---|
| Separate hardware backend and frame gate | Makes warm-hardware behavior and idle frame suppression independently testable while keeping the realtime callback synchronous. |
| Coalesced route recovery | Route preference application can itself produce notifications; one in-flight pass plus one pending pass prevents loops without losing a real device change. |
| Explicit route resolution | `setPreferredInput` is not guaranteed, so requested and actual inputs must remain distinguishable in logs and tests. |
